## P0 findings

### P0-1 — Archive pipeline stalled 5+ weeks; TTL will silently destroy 795M unarchived rows
- Evidence: `parquet_export_state`: 358 days `pending` (2025-08-11→2026-08-03), 1 stuck `exporting` (2026-08-04), 23 `deleted` (last 2026-08-12). Nothing uploaded/deleted in ~5 weeks.
- Live evm_transfers: 795,499,211 rows older than 30d (TTL `block_timestamp + 30d` is live, verified in engine_full). July partition still active: 65.7M rows / 12.73 GiB; 2025-02/03 backfill partitions also active. TTL deletion is lazy (fires on merge) — the next merge of those partitions **deletes rows that were never exported to B2**.
- RETENTION_POLICY comment (config/storage.py:135 "a TTL must never outrun the archive pipeline") is violated in production right now.
- Impact: permanent loss of up to ~333 GiB / 795M rows of transfer history; scanners' historical queries silently lose coverage.
- Fix: unblock the exporter (investigate the stuck 2026-08-04 `exporting` row + why pending never transitions), run backfill export for all pending dates BEFORE any merge touches expired partitions; consider `ttl_only_drop_parts=1` + partition-age gating until archive catches up.

### P0-2 — Cold tier cannot read production exports (layout mismatch, 3-way)
- writer.py:40 + helpers.py:28-41 → `{chain}/{YYYY-MM-DD}/{chain}_{date}.parquet` (day, flat filename).
- duckdb_query.py:103-122, 160-166 → `{chain}/{YYYY}/{MM}/{DD}/{HH}/{chain}_{date}.parquet` (hour dirs).
- compaction.py:16-17 → `hive/chain=…/{month|day}=…/part-*.parquet` (not read by anyone).
- Impact: every byte exported since the pipeline started is unreadable by `duckdb_query`/cold query surface; the "archive" half of the retention contract is not actually queryable. Combined with P0-1, retention currently = delete-without-readable-archive.
- Fix: pick ONE layout (hour dirs or hive) and make writer emit it + reader glob it; add a parity test that round-trips one exported day through duckdb_query.

## P1 findings

### P1-1 — solana_spl_balance_changes duplicates confirmed (NOT migrated, correctly, but dupes exist)
- Live: plain MergeTree, ORDER BY (mint, slot, token_account) — non-unique (TODO.md warning stands).
- Sampled dupes (uniqExact vs count, key +tx_hash): pre-2026-08-01 sample 412,407 rows → 172,710 unique (**~58% dupes**); Aug-2026 sample 500k → 362,517 unique (~27%); Sept (current) 500k → 500k unique (0%). Dup rate decays toward zero at head → historical re-extract overlap, not an ongoing writer bug.
- Impact: balance/delta aggregations double-count historical SPL activity.
- Fix: richer key (+tx_hash) then RMT migration, or dedupe backfill; do NOT RMT with current key (would silently drop legitimate multi-change-per-slot rows — TODO.md is right).

### P1-2 — dex_events duplicate risk: currently clean, key still non-unique-by-tx
- Live: RMT ORDER BY (chain, block_number, log_index) — sampled ranges (eth 26.0M, base 51.0-51.1M, recent 7d/30d windows) show 0 dupes today. But key omits tx_hash; two events in the same tx at same log_index (impossible on EVM) — actually safe on EVM; risk is only re-extract overlap before merge. Deferred migration (TODO) is safe to proceed; must carry column TTLs + projection (TODO already notes this).

### P1-3 — Deferred getLogs returns `[]` = indistinguishable from "no logs" (RC-1 link)
- client.py:862-868: quota-deferred `eth_getLogs` returns `[]` — the same shape as an empty range. Callers that treat `[]` as "no data" and advance state will record **silent data holes** whenever a provider is at degrade level 1 (wide scans >1000 blocks) or 2 (all getLogs).
- ledger.py:794-855 ladder: level 2 defers ALL getLogs; with a `month`/`30d` period budget a provider can sit at 85% for days → weeks of getLogs starvation per account, invisible because the return shape is success-shaped.
- Fix: return `None` (failure shape) or raise a typed QuotaDeferredError from the getLogs path; callers already handle None as failure. At minimum log + metric per deferred getLogs range so holes are detectable.

### P1-4 — Ledger `_load` fold can extend a park indefinitely
- ledger.py:433: `existing.reset_at = max(existing.reset_at, budget.reset_at)` when folding legacy per-key budgets — one stale far-future reset_at parks the whole account past its real window. Low frequency (one-time migration) but silent. Fix: clamp fold to the account's own period boundary.

### P2-2 — Migration 017/018 state: confirmed
- 017 invalid (Code 36, MODIFY ORDER BY can't append existing column) — header documents it; live sorting_key confirms 018 form applied. Do-not-retry note correct.
- tx_log_key IS populated on INSERT: clickhouse.py:412 `_transfer_dedup_key(key)` = `"{block}:{tx_hash}:{log_index}"`, named in INSERT column list (clickhouse.py:428). Pre-migration rows read `''` (no default) — expected per migration design.
- App dedup `_existing_transfer_keys` (clickhouse.py:283-322) queries `(block_number, tx_hash, log_index)` over `chain + block_number BETWEEN` — index-friendly (prefix of ORDER BY). Span cap 50k blocks (clickhouse.py:67) prevents whole-chain scans. Agrees with tx_log_key component order (pinned by unit test).
- Residual overlap risk: rows inserted BEFORE 018 have tx_log_key='' — a re-extract of an old range inserts new rows with a real key; RMT sees ('' vs 'key') as DIFFERENT rows → old+new both survive merge → duplicates for any pre-018 range that gets re-extracted. Mitigated only by the app-layer existence check (which does catch it while the span ≤50k). Fix: one-time backfill `UPDATE tx_log_key = concat(...)` (migration 018's own commented-out step) or accept app-layer guard.

### P2-3 — Write path: sound
- ch_write_pool.py: bounded ThreadPoolExecutor (CH_WRITE_THREADS=4), per-loop semaphore backpressure, thread-local clients. No unbounded queue. `_existing_transfer_keys` cost is one indexed range query per batch — acceptable.
- Batch inserts via single `client.execute(... VALUES, rows)` — correct CH pattern.

### P2-4 — Disk hygiene
- evm_transfers 332.92 GiB (55 parts) dominates; Aug-2026 partition alone 240.31 GiB / 1.22B rows. dex_events 12.69 GiB, address_activity 11.62 GiB, holder_balances MV target 10.51 GiB. Growth ~1.7B rows total; once TTL+archive work, hot window drops to ~30d (~90 GiB).
- No runaway part counts (max 55 parts) — insert batching healthy.

## Verdict
**C+** — schema/migration layer is in good shape (018 applied and populated, TTL metadata aligned, write path bounded), but the cold-storage chain is broken end-to-end: exports stalled 5 weeks, layout three-way mismatch, and the live 30d TTL is now ahead of the archive — 795M rows are one merge away from silent, unarchived deletion. Fix P0-1/P0-2 before anything else.
